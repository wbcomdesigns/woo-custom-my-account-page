# Security review - Custom My Account Page for WooCommerce 1.7.1

Date: 2026-10-06. Scope: diff from v1.7.0 (patch release; the full-plugin audit ran for 1.7.0).
Method: mechanical sweep (`security-sweep.sh --baseline v1.7.0`), diff review of every security-relevant change, runtime checks on a local WooCommerce site (Reign, BuddyX, BuddyX Pro, Storefront, Twenty Twenty-Five).

Verdict: no Critical or High findings. No new sweep findings against v1.7.0. One hardening fix shipped (settings allowlist).

## Findings fixed in 1.7.1

| Sev | Where | Attacker story | Fix |
|---|---|---|---|
| Low | `admin/class-woo-custom-my-account-page-admin.php` (`wcmp_general_settings_callback`) | An administrator (or a forged request carrying a valid settings nonce) could store any string as `menu_style` / `sidebar_position`. Output was already escaped and fell back safely, so there was no injection, only junk stored. | Allowlists [sidebar, tab] and [left, right]; anything else saves the default. Verified: `menu_style=hacker` is stored as `sidebar`. |

## G1 - mechanical sweep

`security-sweep.sh . --baseline v1.7.0`: no CRITICAL patterns. Same counts as v1.7.0:

- `files-superglobal` (2): unchanged avatar upload handler; see "Scanner-visible but safe".
- `no-abspath-guard` (4): `blocks/my-account/editor.asset.php` (returns an array, no output) and `bin/phpstan-bootstrap.php` (dev-only, not in the release zip; verified with `unzip -l`); the other two carry their guard below the sweep's 40-line window. Same count as v1.7.0.
- REST routes: 0.

## G2 - authorisation

The plugin registers no REST routes. Its request surfaces are unchanged in 1.7.1:

- `wcmp_add_field` (admin AJAX): nonce `wcmp_add_field` + `manage_options`. Unchanged.
- `wcmp_print_avatar_form` (WC AJAX): logged-in only, returns the current user's own form. Runtime: logged-out POST returns HTTP 200 with an empty body.
- Avatar upload / reset (`template_redirect`): nonce + logged-in + setting on; acts only on the current user's meta. Unchanged.
- Role-restricted endpoints: customer allowed, subscriber redirected to My Account, logged-out visitor gets the login form (re-verified on 1.7.1 in the browser).
- New empty-endpoint notice: the "Add content to this page" admin link is printed only when `current_user_can( 'manage_options' )`; a restricted endpoint is redirected by `wcmp_restrict_endpoint_access()` before content renders.

## G3 - diff review (v1.7.0..1.7.1)

- `get_form_allowed_html()` gained `role`, `aria-*` (modal, labelledby, describedby, live, hidden), `hidden`, `form` on buttons, `h2`, `img` `srcset/loading/decoding/hidden`, and `data-*` on `form`. The filtered HTML is the plugin's own template, rendered server-side for the current user; no user-controlled markup passes through it. `style`, `on*` handlers and `script` stay disallowed.
- Avatar template: every attribute is escaped (`esc_attr`, `esc_attr_e`, `esc_html_e`); the limits come from class constants, not request data.
- Avatar JS: the chosen file name is written with `.text()`, the preview uses a local `URL.createObjectURL()` blob; nothing from the file is inserted as HTML. The browser-side size/type check is a convenience; the server check (`wp_check_filetype_and_ext()` allowlist + `AVATAR_MAX_BYTES`) is unchanged and authoritative.
- Empty-endpoint notice: message built from `esc_html__()` and `esc_url( admin_url() )`, then `wc_print_notice()` (which runs `wp_kses_post`).
- Menu-order pruning (`wcmp_prune_endpoint_order`): only reads ids already sanitized on save (`sanitize_key`); drops unknown ids; no new output.
- Admin builder: `.hide-show-trigger` / `.remove-trigger` became `<button type="button">`; the removal still only marks the key in the posted form, and the settings save (nonce + `manage_options`) is unchanged. Removed `wcmp_fa_to_dashicon()` and two unused localized strings.

## Scanner-visible but safe

- `files-superglobal` (2, `public/class-woo-custom-my-account-page-public.php`): avatar upload reads `$_FILES` only after nonce + logged-in + setting checks; type checked with `wp_check_filetype_and_ext()` against `AVATAR_TYPES` (JPEG/PNG/GIF/WebP, no SVG), size capped at `AVATAR_MAX_BYTES` (2 MB), stored via `media_handle_upload()`.
- `data-*` wildcard on `form` in the kses allowlist: applies only to the plugin's own avatar template output.

## Plugin Check (built zip, errors only)

87 errors on 1.7.1 vs 79 on 1.7.0 (same check on the v1.7.0 release asset). The only change: 8 new `WordPress.WP.I18n.TextDomainMismatch` in `lib/wbcom-settings/class-wbcom-settings-page.php`, from the shared settings shell update to 1.0.4/1.0.5. Intentional: the shell uses its own `wbcom-settings` text domain and loads its own translations (`load_textdomain()` from `WP_LANG_DIR/plugins` or its bundled `languages/`), so one translation covers every plugin bundling it. Plugin-owned errors: unchanged (prefixing of template-scope variables, `load_plugin_textdomain`, `trademarked_term`, readme short description) - existing backlog, not new.
